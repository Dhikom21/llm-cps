0 · Pi housekeeping

any time

Shut down / reboot cleanly

Never pull the USB-C power while the Pi is running — it can corrupt the SD card. Always shut down first, then unplug. Power must be off before you change any wiring.

bash 
sudo shutdown -h now      # power off
sudo reboot               # restart

Who and where am I?

bash 
whoami            # dp
hostname          # cps-pi
hostname -I       # this Pi's IP address(es)
uname -a          # kernel + architecture
pwd               # current folder
If hostname -I prints nothing, the Pi has no network at all — it is not an SSH problem, it is a cable / Wi-Fi problem.

Install the Python libraries the project needs

bash 
sudo apt update
sudo apt install -y python3-gpiozero python3-w1thermsensor i2c-tools
pip install adafruit-circuitpython-ads1x15 --break-system-packages

Prove the libraries import

This was milestone M1. If it prints, the software side is ready and anything that fails afterwards is wiring.

bash 
python3 -c "import gpiozero, w1thermsensor; print('libraries OK')"
Expected: libraries OK

1 · Enable the 1-Wire and I²C buses

once, then reboot

The GPIO pins are plain digital pins until you tell the firmware that pin 7 should speak 1-Wire and pins 3/5 should speak I²C. That switch lives in the boot config, and raspi-config edits it for you.

bash 
sudo raspi-config nonint do_onewire 0     # 0 = enable
sudo raspi-config nonint do_i2c 0
sudo reboot

Verify it stuck

bash 
grep -iE "w1|i2c" /boot/firmware/config.txt
lsmod | grep -E "w1_gpio|w1_therm|i2c_dev"
Expected in config.txt: dtoverlay=w1-gpio and dtparam=i2c_arm=on

2 · Network and SSH troubleshooting

run on the laptop unless noted

These are the commands that untangled the "SSH just hangs" problem. The root cause turned out to be two machines answering to the same IP address.

Find the Pi on the network — from Windows PowerShell

powershell 
ping cps-pi.local
arp -a                                    # list every IP+MAC the laptop has seen
Test-NetConnection 192.168.1.45 -Port 22  # is the SSH port reachable?
In ping output, if SourceAddress equals RemoteAddress and the round-trip is 0 ms, you are pinging your own laptop, not the Pi.

SSH in, with full diagnostics

bash 
ssh dp@192.168.1.45
ssh -v dp@192.168.1.45      # -v shows exactly where it stalls
Connection timed out during banner exchange means the TCP port opened but the SSH handshake never completed — classic sign of an IP conflict (two devices holding the same address).

Confirm the conflict — on the Pi, with a monitor attached

bash 
hostname -I
sudo journalctl -u ssh -n 30 --no-pager
The smoking gun we saw: timeout before authentication for connection from 192.168.1.44 to 192.168.1.45

Path-MTU check (rules out fragmentation)

bash 
ping -M do -s 1400 192.168.1.45   # large packet, do-not-fragment

Make WSL able to reach the Pi

By default WSL2 sits behind its own NAT and cannot see your LAN. Create C:\Users\dhikom\.wslconfig on Windows with the lines below, then wsl --shutdown and reopen WSL.

ini 
[wsl2]
networkingMode=mirrored
firewall=false

3 · DS18B20 temperature sensors (1-Wire)

milestone M2

Two DS18B20 sensors share one three-wire bus: VDD, GND and DATA. A single 4.7 kΩ pull-up resistor between DATA and VDD serves the whole bus, no matter how many sensors hang off it. Each sensor carries a unique 64-bit ID burned in at the factory, which is how the Pi tells them apart on a shared wire.

Does the kernel see the sensors?

bash 
ls /sys/bus/w1/devices/
Good: 28-xxxxxxxxxxxx 28-yyyyyyyyyyyy w1_bus_master1
Bad: only w1_bus_master1 — no sensor is answering.
When we saw only w1_bus_master1, the cause was the wrong resistor value. Swapping in a real 4.7 kΩ made both 28-* devices appear immediately.

Read the raw kernel file (no Python involved)

Useful for proving the sensor works before you blame your code. The temperature is the number after t=, in thousandths of a degree.

bash 
cat /sys/bus/w1/devices/28-*/w1_slave
Expected: a line ending YES, then a line ending t=22937 → 22.937 °C

One sensor, one reading (Python)

python 
from w1thermsensor import W1ThermSensor

sensor = W1ThermSensor()
print(sensor.get_temperature())
The class name is W1ThermSensor — capital T and capital S. W1Thermsensor raises ImportError: cannot import name.

Both sensors, with their IDs

bash 
python3 -c "
from w1thermsensor import W1ThermSensor
for s in W1ThermSensor.get_available_sensors():
    print(s.id, round(s.get_temperature(), 4))"
First real reading of the project: 22.9375 °C

Watch the temperature live

Pinch a sensor between your fingers and you should see it climb about a degree every few seconds. This is the quickest proof that the sensor is genuinely sensing and not returning a cached value.

bash 
watch -n 2 'python3 -c "
from w1thermsensor import W1ThermSensor
for s in W1ThermSensor.get_available_sensors():
    print(s.id, round(s.get_temperature(), 4))"'

Same thing as a one-line loop

Use this version if a multi-line loop loses its line breaks when pasted — that is what produced syntax error near unexpected token 'done'.

bash 
while true; do python3 -c "from w1thermsensor import W1ThermSensor;[print(s.id, round(s.get_temperature(),4)) for s in W1ThermSensor.get_available_sensors()]"; echo ---; sleep 2; done

4 · Grove relay (the heater actuator)

milestone M2

The relay is a digital output: drive GPIO17 HIGH and the relay coil pulls in with an audible click and a lit LED. That click is the whole test — you do not need anything connected to the relay's output terminals to prove it works.

One click on, one click off

bash 
python3 -c "
from gpiozero import OutputDevice
import time
relay = OutputDevice(17, active_high=True, initial_value=False)
relay.on();  print('ON  - listen for the click'); time.sleep(2)
relay.off(); print('OFF - second click')"

Blink it five times

bash 
python3 -c "
from gpiozero import OutputDevice
import time
r = OutputDevice(17)
for i in range(5):
    r.on();  print('ON');  time.sleep(1)
    r.off(); print('OFF'); time.sleep(1)"
The Grove cable ends in a single 4-way female housing. It cannot plug onto four adjacent Pi header pins, because the Grove pin order (SIG · NC · VCC · GND) matches no run of Pi pins — and forcing it would put 5 V onto a 3.3 V-only GPIO and destroy it. Use three male-female jumpers as extenders: SIG → pin 11, VCC → pin 2, GND → pin 6.

5 · Piezo buzzer (the fire alarm)

milestone M3

A bare two-pin piezo draws only a few milliamps, so it can be driven straight from a GPIO with no transistor. But it is a passive element — it needs an alternating tone, not a steady HIGH. Plain on() produces silence; PWM produces sound.

Beep for one second

bash 
python3 -c "
from gpiozero import PWMOutputDevice
import time
b = PWMOutputDevice(27, frequency=2000)
b.value = 0.5; print('beep'); time.sleep(1)
b.off()"
Expected: a 2 kHz tone for one second.

Play actual notes

bash 
python3 -c "
from gpiozero import TonalBuzzer
from gpiozero.tones import Tone
import time
b = TonalBuzzer(27)
for note in ['A4','C5','E5']:
    b.play(Tone(note)); time.sleep(0.4)
b.stop()"

Alarm pattern (what the fire scenario will use)

bash 
python3 -c "
from gpiozero import PWMOutputDevice
import time
b = PWMOutputDevice(27, frequency=2500)
for i in range(6):
    b.value = 0.5; time.sleep(0.25)
    b.value = 0.0; time.sleep(0.25)
b.off()"

6 · ADS1115 + SEN0570 smoke sensor (I²C)

milestone M3

The Raspberry Pi has no analogue inputs at all — every GPIO can only report HIGH or LOW. The smoke sensor outputs a varying voltage, so the ADS1115 sits between them: it measures that voltage and reports it to the Pi as a number over the I²C bus.

Is the ADC on the bus?

bash 
i2cdetect -y 1
Expected: 48 in the grid (row 40, column 8) — the ADS1115's default address with its ADDR pin tied to GND.
A blank grid means wiring: check SDA on pin 3, SCL on pin 5, VDD on 3.3 V, GND to GND — and that I²C is enabled (section 1).

Read one analogue channel

python 
import board, busio
import adafruit_ads1x15.ads1115 as ADS
from adafruit_ads1x15.analog_in import AnalogIn

i2c = busio.I2C(board.SCL, board.SDA)
ads = ADS.ADS1115(i2c)
chan = AnalogIn(ads, ADS.P0)          # smoke sensor A-out on A0

print("raw:", chan.value)             # 16-bit count
print("volts:", round(chan.voltage, 3))

Watch it while you wave smoke at it

bash 
python3 -c "
import board, busio, time
import adafruit_ads1x15.ads1115 as ADS
from adafruit_ads1x15.analog_in import AnalogIn
i2c = busio.I2C(board.SCL, board.SDA)
chan = AnalogIn(ADS.ADS1115(i2c), ADS.P0)
while True:
    print(chan.value, round(chan.voltage, 3)); time.sleep(0.5)"
Note the resting voltage in clean air first — that baseline is what your smoke threshold has to sit above.

7 · The closed loop on real hardware

milestone M3 → M4

This is the smallest complete cyber-physical loop: perceive the temperature, decide against a setpoint, act on the relay — then repeat forever. No LLM yet, no network, no database. Everything the project adds later hangs off this three-line skeleton.

hw_test.py

python 
"""hw_test.py — bare-metal closed loop: sensor -> rule -> relay."""
from w1thermsensor import W1ThermSensor
from gpiozero import OutputDevice
import time

SETPOINT = 25.0

sensors = W1ThermSensor.get_available_sensors()
print("sensors found:", [s.id for s in sensors])

heater = OutputDevice(17, active_high=True, initial_value=False)

try:
    while True:
        temp = sensors[0].get_temperature()      # PERCEIVE
        want_on = temp < SETPOINT                # DECIDE
        if want_on != heater.is_active:          # ACT (only on change)
            heater.on() if want_on else heater.off()
        print(f"{time.strftime('%H:%M:%S')}  {temp:6.2f} C  "
              f"heater={'ON ' if heater.is_active else 'OFF'}")
        time.sleep(2)
except KeyboardInterrupt:
    heater.off()
    print("\nstopped, heater off")
bash 
cd ~/llm-cps/lab_practice
python3 hw_test.py
Always turn the heater off in the except branch. If you Ctrl-C out while the relay is energised it stays energised — the physical world does not reset when your program exits.

8 · Running the project code on the Pi

milestone M3 → M5

Get the code onto the Pi

scp failed because the laptop was on the LTU network (130.x) while the Pi was on the project router (192.168.1.x) — two networks that cannot reach each other. Git worked because both machines reach GitHub independently, so the code travels via the internet rather than across the LAN.

bash 
git clone https://github.com/<user>/llm-cps.git
cd llm-cps
git pull                      # fetch later changes
git log --oneline -5          # confirm you have the newest commit

Hardware driver self-test

real_hardware.py and fake_hardware.py expose the identical interface — read_temperature(), read_smoke(), set_heater(), set_buzzer() — so the agent above them never knows whether it is driving a simulation or a real room.

bash 
cd ~/llm-cps/lab_practice
python3 real_hardware.py
Its constructor initialises the buzzer and the ADS1115, so it raises an exception until both are wired. Wire them first, or temporarily use python3 fake_hardware.py to test everything above the driver.

Swap simulation for reality in one line

python 
# from fake_hardware import get_room     # simulated
from real_hardware import get_room         # the actual Pi

room = get_room()
print(room.read_temperature(), room.read_smoke())
room.set_heater(True)
room.set_buzzer(False)

Common errors seen along the way

MessageCause and fix
cannot import name W1Thermsensor Capitalisation. The class is W1ThermSensor.
ModuleNotFoundError: db Run the script from inside lab_practice, not from the repo root.
syntax error near unexpected token 'done' A multi-line shell loop lost its newlines on paste. Use the one-line form.
ConnectionRefusedError on MQTT Mosquitto is not running: docker compose up -d in lab_practice.
cd /mnt/c/... : No such file /mnt/c only exists inside WSL on Windows, never on the Pi.
