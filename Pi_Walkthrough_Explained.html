1What we are actually building

A cyber-physical system is any system where software senses the real world, decides something, and then changes the real world. That is the entire idea. It is always the same three beats, repeated forever:

PerceiveHow warm is the room right now?
DecideIs that too cold?
ActSwitch the heater on.

Then it loops back to the beginning, because acting changes the world, which changes what you perceive next time. That feedback is what makes it a loop rather than a script.

Analogy. You are in a room and feel cold. Your skin is the sensor. Your brain comparing "cold" against "comfortable" is the decision. Your hand reaching for the thermostat is the actuator. Thirty seconds later your skin feels the room again — that is the loop closing. Everything we build on the Pi is a mechanical version of exactly this, and later on the LLM takes over the job of the brain.

So the work ahead has a shape: first give the Pi skin (a temperature sensor), then give it a hand (a relay that switches a heater), then write the few lines of Python that connect the two. Everything else — the database, the dashboard, the language model — is decoration hanging off that core loop.

2The Pi and its 40 pins

A Raspberry Pi is an ordinary small Linux computer, with one extra thing a laptop does not have: a double row of 40 metal pins along one edge, called the GPIO header. GPIO stands for General Purpose Input/Output, which is a long way of saying "pins you control from your own code".

Each pin does one of three jobs. Some are permanently wired to power — a couple give 5 volts, a couple give 3.3 volts. Some are permanently wired to ground, which is the return path every circuit needs. The rest, the majority, are the programmable ones: your code can either drive them (force them to 3.3 V or 0 V, to switch something on or off) or read them (ask whether something out there is holding them high or low).

Analogy. Think of the header as 40 sockets on a wall. A few are mains outlets you can only take power from. A few are drains. The rest are light switches that your program can flip — or doorbells your program can listen to. The physical wiring decides which device is on which socket; your code decides what to do with it.

Two numbering systems exist for these pins and they are a constant source of confusion. The physical pin number counts along the header, 1 to 40, like seats in a row. The GPIO number is the chip's own internal name for that pin. They do not match: physical pin 11 is GPIO17. Wiring diagrams usually talk in physical pins because you are counting holes with your finger; Python libraries usually talk in GPIO numbers. When you read OutputDevice(17) in our code, that is GPIO17, which is the eleventh pin along.

The breadboard

A breadboard is a plastic slab full of holes that lets you join wires without soldering. The rule that matters: each row of five holes is one single electrical connection. Push two wires into the same row and they are joined, as surely as if you had twisted them together. Push them into different rows and they are not.

One extra wrinkle: a row is split down the middle by a channel. The holes labelled a b c d e form one connection, and f g h i j on the same numbered row form a separate one. So "row 6" is really two independent connections facing each other.

This is why our sensor legs sit in rows 5, 6 and 7 on the f–j side, and why the jumper going to the Pi has to be plugged into the same side of the same row — otherwise it is connected to nothing at all.

3Teaching the pins a language

Out of the box, a GPIO pin only understands "high" and "low". But our temperature sensor does not communicate in high and low — it communicates in a protocol, a specific rhythm of pulses with a defined meaning, called 1-Wire. Likewise the analogue-to-digital converter we add later speaks a different protocol called I²C.

The Pi's firmware can turn certain pins into protocol speakers, but you have to ask. That request happens at boot time, through a setting file, and raspi-config is the tool that edits it for you:

bash 
sudo raspi-config nonint do_onewire 0     # 0 means "enable"
sudo raspi-config nonint do_i2c 0
sudo reboot

The reboot is not optional. These settings are read once, while the Pi is starting up, before Linux is fully awake — so a change only takes effect on the next boot.

Analogy. The pins are staff who all speak plain English. Enabling 1-Wire is sending one of them on a course to learn Morse code. Until they come back from the course — the reboot — they still only speak English, and your Morse-code sensor gets no reply.

Once it has rebooted, you can check the training took:

bash 
grep -iE "w1|i2c" /boot/firmware/config.txt
You want to see: dtoverlay=w1-gpio and dtparam=i2c_arm=on. If those lines are present, the pins now speak the protocols and any remaining problem is in the wiring.

4Getting a keyboard onto the Pi

The Pi has no screen. You control it over the network from your laptop using SSH, which gives you a text terminal on the Pi inside a window on your laptop. Anything you type runs over there.

bash 
ssh dp@192.168.1.45

Read that as: connect to the machine at that address and log in as the user dp. For this to work, the two machines have to be on the same network and the Pi has to have an address of its own.

Why ours hung, and how we found out

Our first attempts simply froze with no error. The useful trick is the -v flag, which makes SSH narrate every stage of the handshake so you can see the exact point it stops:

bash 
ssh -v dp@192.168.1.45

It stopped at Connection timed out during banner exchange. That one phrase told us a great deal. The "banner" is the first sentence each side speaks when the connection opens. Reaching that stage means the network path was fine and something was listening — but then the conversation died. The classic cause is that two machines are answering to the same address, so half the replies go to the wrong one. The Pi's own log confirmed it, by recording a connection it had never managed to finish:

bash 
sudo journalctl -u ssh -n 30 --no-pager
Analogy. You phone a house where two people share one handset. You say hello; one of them hears you, but the other one is the one holding the microphone. Both ends wait politely for a reply that will never come. Nothing is broken — the address is just ambiguous.

The lesson worth keeping: when a network tool hangs, do not guess. Every layer has a command that answers one question, and you walk up the layers until one fails. ping asks "does this address exist?". Test-NetConnection <ip> -Port 22 asks "is anything listening on the SSH port?". ssh -v asks "how far does the conversation get?". The first one that misbehaves is where your problem lives.

5Step one of the loop: sensing

The DS18B20 is a temperature sensor the size of a grain of rice on three legs: power, ground, and data. What makes it pleasant to work with is that it is not really a lump of metal that changes resistance — it has a tiny computer inside. It measures its own temperature, converts it to a number, and sends that number down the data wire as digits. You never deal with voltages or calibration curves; you receive a number.

Better still, several sensors can share one data wire. Each one leaves the factory with a unique 64-bit serial number burned into it, so when the Pi calls out on the shared wire, only the sensor whose number was called answers.

Analogy. One telephone line into a house with several people on it. The Pi calls out "number 28-a1b2, what's your temperature?" and only that person speaks. That is why two sensors need no extra pins — just the same three wires.

Why the 4.7 kΩ resistor exists

The shared data wire needs a rule for what "nobody is talking" looks like. The resistor gently pulls the wire up to 3.3 V, so idle means high. To send a zero, a sensor yanks the wire down to ground, which easily overpowers that gentle pull. When it lets go, the resistor pulls the line back up again.

It is one resistor for the whole bus, not one per sensor — the wire needs the rule, not each talker. Get its value wrong and the line either cannot be pulled down or cannot spring back fast enough. That is exactly what happened to us: with the wrong resistor fitted, the Pi found no sensors at all. Replacing it with a true 4.7 kΩ made both appear instantly.

Seeing the sensors without writing any code

Linux presents the 1-Wire bus as a folder. Each sensor that answers turns up as a subfolder named after its serial number. So a plain directory listing is your wiring test:

bash 
ls /sys/bus/w1/devices/
Two sensors wired correctly: 28-xxxxxxxxxxxx  28-yyyyyyyyyyyy  w1_bus_master1
Nothing answering: only w1_bus_master1 — that entry is the Pi's own bus controller, which is always there whether or not anything is plugged in.

You can even read a temperature with no Python whatsoever, because each sensor's folder holds a file containing its latest reading:

bash 
cat /sys/bus/w1/devices/28-*/w1_slave

The output ends with something like t=22937, which is the temperature in thousandths of a degree — 22.937 °C. This is a genuinely useful habit: prove the hardware works at the lowest possible level first, so that when your Python misbehaves you already know the sensor is innocent.

The same thing in Python

python 
from w1thermsensor import W1ThermSensor

for sensor in W1ThermSensor.get_available_sensors():
    print(sensor.id, round(sensor.get_temperature(), 4))
LineWhat it does
from w1thermsensor import W1ThermSensor Borrow the ready-made DS18B20 class from the library. It does the tedious part — finding the folders, reading the file, handling the thousandths — so we don't. Watch the capitals: W1ThermSensor. Writing W1Thermsensor gives ImportError: cannot import name, which cost us a few minutes.
W1ThermSensor.get_available_sensors() "Go and look in that folder, and hand me back one object for every sensor you find." Returns a list — empty if the wiring is wrong, two entries for us.
for sensor in …: Deal with each sensor in turn. Written this way the code doesn't care whether you have one sensor or five; it just works through whatever is there.
sensor.id That sensor's unique serial number. This is how you tell your two identical-looking sensors apart in the data later — one is at the radiator, one is by the window.
sensor.get_temperature() Triggers a fresh measurement and returns degrees Celsius as a normal Python float. This single call is the "perceive" beat of the whole cyber-physical loop.
round(…, 4) Cosmetic. The sensor's real resolution is 1/16 °C, so readings land on values like 22.9375 — four decimals keeps the true precision without a wall of digits.
The first real reading of this project was 22.9375 °C. That number is the moment the project stopped being a simulation.

Proving it is really sensing

A single reading is not proof. A value can be stale, cached, or hard-coded. The honest test is to change the world and watch the number follow — so pinch a sensor between your fingers and watch it climb:

bash 
watch -n 2 'python3 -c "
from w1thermsensor import W1ThermSensor
for s in W1ThermSensor.get_available_sensors():
    print(s.id, round(s.get_temperature(), 4))"'

watch -n 2 simply re-runs the command every two seconds and redraws the screen, so you get a live display without writing a loop. Within a few seconds of holding a sensor you should see it rise a degree or more, then drift back down when you let go. That is proof.

6Step two: acting on the world

Sensing is only half a loop. To close it, the Pi needs a hand — and the hand here is a relay.

A relay is an electrically operated switch. A small current from a GPIO pin energises a coil, the coil becomes a magnet, the magnet drags a metal contact across, and that contact closes a completely separate circuit which can carry far more power than the Pi could ever supply.

Analogy. The Pi is a person who can only whisper, and the heater responds only to shouting. The relay is a megaphone with a button: a gentle press on the button produces a very loud noise. The two sides never touch, which is exactly the point — the heater's power cannot flow back and destroy the Pi.

That separation is why the relay is the single most important safety component on the board, and it is why the test for it is so satisfying: energising the coil makes a clearly audible click. You do not need anything wired to the output side to know it works — the click and the LED tell you the software reached the physical world.

python 
from gpiozero import OutputDevice
import time

relay = OutputDevice(17, active_high=True, initial_value=False)

relay.on()                 # click
time.sleep(2)
relay.off()                # click again
LineWhat it does
from gpiozero import OutputDevice gpiozero is the Pi's friendly GPIO library. OutputDevice is its most basic building block: a pin you drive, as opposed to a pin you read.
OutputDevice(17, …) Claim GPIO17 — physical pin 11 — and from now on this object is that pin. The library reserves it, so a second program trying to grab the same pin gets a clear error instead of a silent fight.
active_high=True Declares which voltage means "on". Our relay activates when the pin is driven high, so on() should send it high. Plenty of relay modules are the opposite — active-low — and with those you set this to False, otherwise on() would switch the heater off. It is a one-word fix for a very confusing symptom.
initial_value=False Start in the off state. Without it there is a brief window at program start where the pin's state is undefined — meaning the heater could twitch on for a moment every time you launch your script. On real hardware, defining the starting state matters.
relay.on() / relay.off() Drive the pin high / low. This is the "act" beat of the loop — the one line in the whole project where software becomes physics.
time.sleep(2) Do nothing for two seconds, so you can hear both clicks as separate events rather than one blur.
Why the Grove cable needed adapting. Our relay came with a four-way connector in one moulded block. It cannot plug straight onto four Pi pins, because its wire order (SIG · NC · VCC · GND) does not match any four consecutive pins on the Pi header — and lining it up by force would put 5 V onto a 3.3 V-only GPIO and destroy the pin. Three male-female jumpers used as extenders solve it: SIG to pin 11, VCC to pin 2, GND to pin 6. The general lesson is that a connector fitting physically means nothing; only the pin order matters.

7Making noise: why a buzzer is different

The buzzer is our alarm for the fire scenario. Wiring it is trivial — a bare piezo draws so little current that it connects straight to a GPIO pin and ground with no transistor — but driving it catches everyone out the first time.

A piezo element makes a sound by flexing. Apply a voltage and it bends once, with a faint tick. Hold that voltage and it just stays bent, silently. To produce a continuous tone you have to make it flex back and forth thousands of times a second, which means the voltage has to keep switching. A steady on() gives you silence.

Analogy. A guitar string. Pull it aside and hold it there and you hear nothing. Let it vibrate and you get a note, and how fast it vibrates sets the pitch. The piezo is the same: it needs to be shaken, not held.

The shaking is done with PWM — Pulse Width Modulation — which is just the pin being switched on and off very rapidly by hardware, so your program does not have to sit in a loop doing it:

python 
from gpiozero import PWMOutputDevice
import time

buzzer = PWMOutputDevice(27, frequency=2000)

buzzer.value = 0.5         # start the tone
time.sleep(1)
buzzer.off()
LineWhat it does
PWMOutputDevice(27, …) Like OutputDevice, but this pin can switch itself rapidly instead of simply sitting high or low. GPIO27 is physical pin 13.
frequency=2000 Switch 2000 times per second — so the piezo flexes 2000 times per second, and you hear a 2 kHz tone. Change this number and the pitch changes. This is the one setting that decides what the alarm sounds like.
buzzer.value = 0.5 The duty cycle: what fraction of each cycle the pin spends high. 0.5 means half on, half off — a clean square wave, and the loudest, cleanest tone. 0 is silence, 1 is permanently on which, as above, is also silence.
buzzer.off() Stop switching. Sets the duty cycle to zero and the noise ends.

To make it sound like an alarm rather than a test tone, pulse it — on for a quarter second, off for a quarter second — by setting value back and forth in a short loop. Urgency in an alarm comes from the rhythm, not the pitch.

8Reading something that isn't yes/no

Now a genuine limitation. The Raspberry Pi has no analogue inputs at all. Every one of its GPIO pins can report exactly two things: high or low. It has no way to tell you that a wire is sitting at 1.8 volts.

Our smoke sensor, unlike the DS18B20, has no computer inside. It simply outputs a voltage that rises as more smoke reaches it — a little in clean air, more in light smoke, more still in heavy smoke. The Pi cannot read that. The two are physically incompatible.

The fix is a separate chip, the ADS1115, an analogue-to-digital converter. It measures the voltage properly, turns it into a number, and hands that number to the Pi over the I²C bus — a form of communication the Pi can understand.

Analogy. The Pi can only ask "is the bucket empty or not?". The smoke sensor answers in inches of water. The ADS1115 is an assistant with a ruler: it measures the water, reads the number out loud, and now the Pi has something it can work with.

Check the chip is present before writing code

bash 
i2cdetect -y 1

This scans the I²C bus and prints a grid of every device that answers. Each device has an address, and the ADS1115's default is 0x48. Seeing 48 appear in the grid means the chip is powered and talking — again, proving the hardware before trusting any Python.

python 
import board, busio
import adafruit_ads1x15.ads1115 as ADS
from adafruit_ads1x15.analog_in import AnalogIn

i2c  = busio.I2C(board.SCL, board.SDA)
ads  = ADS.ADS1115(i2c)
chan = AnalogIn(ads, ADS.P0)

print("raw:  ", chan.value)
print("volts:", round(chan.voltage, 3))
LineWhat it does
busio.I2C(board.SCL, board.SDA) Open the I²C bus. SCL is the clock line and SDA the data line — the two wires every I²C device shares. board.SCL just means "this particular board's clock pin", so the same code runs on different hardware.
ADS.ADS1115(i2c) "On that bus, there is an ADS1115." From here on, this object represents the chip.
AnalogIn(ads, ADS.P0) The chip has four input channels. This picks channel 0, which is where the smoke sensor's output is wired. Point a second AnalogIn at ADS.P1 and you could read a second analogue sensor with no extra hardware.
chan.value The raw 16-bit count straight from the converter. Useful for thresholds, meaningless as a physical quantity.
chan.voltage The same measurement converted into actual volts. This is the one to log, because volts mean something to a human reading your report.
Write down the resting value in clean air. Smoke sensors have no absolute scale — the reading only means something relative to their own baseline, which drifts with humidity and with the sensor's age. Your alarm threshold has to be defined as a rise above that baseline, not as a fixed number, or it will either never trigger or never stop.

9Closing the loop — and adding the LLM

Every piece now exists: something that senses, something that acts, and a Pi in the middle. Joining them into a loop takes about fifteen lines, and those fifteen lines are the actual cyber-physical system. Everything after this point in the project is refinement.

python 
from w1thermsensor import W1ThermSensor
from gpiozero import OutputDevice
import time

SETPOINT = 25.0

sensors = W1ThermSensor.get_available_sensors()
heater  = OutputDevice(17, active_high=True, initial_value=False)

try:
    while True:
        temp = sensors[0].get_temperature()        # PERCEIVE
        want_on = temp < SETPOINT                  # DECIDE
        if want_on != heater.is_active:            # ACT, only on change
            heater.on() if want_on else heater.off()
        print(f"{temp:6.2f} C  heater={'ON ' if heater.is_active else 'OFF'}")
        time.sleep(2)
except KeyboardInterrupt:
    heater.off()
    print("\nstopped, heater off")
LineWhat it does
SETPOINT = 25.0 The goal, in one place at the top. Control code should always have its target named and visible rather than buried as a bare number halfway down.
while True: Run forever. A control system is not a task that finishes — it is a process that keeps the world in a desired state, so it has no natural end.
temp = sensors[0].get_temperature() Perceive. Ask the first sensor what it reads, right now.
want_on = temp < SETPOINT Decide. The entire policy, in one comparison: too cold means the heater should be on. This single line is the piece the LLM will eventually replace.
if want_on != heater.is_active: Only act when something needs to change. Without this guard the relay would be commanded every two seconds forever. Relays are mechanical and wear out, so needless switching is real damage — and in a heating system, rapid on-off cycling ("chattering") is hard on the equipment too. Compare desired state against actual state and act only on the difference.
heater.on() if want_on else heater.off() Act. The loop touches the physical world.
time.sleep(2) Pause before looking again. This sets the loop's tempo, and the right value depends on the physics: rooms warm over minutes, so polling every two seconds is already generous. Sampling far faster than the process can change just burns CPU and fills your database with duplicates.
except KeyboardInterrupt: heater.off() The most important three lines on this page. Press Ctrl-C without this and your program exits with the relay still energised and the heater still running — because unlike a variable, the physical world does not reset when your process dies. Always leave the hardware in a safe state on the way out.

Why there are two hardware files

The project carries real_hardware.py and fake_hardware.py, and they expose exactly the same four functions: read_temperature(), read_smoke(), set_heater(), set_buzzer(). One talks to the sensors and relay; the other invents plausible numbers in software.

Because the function names and arguments match, everything built on top — the agent, the guardrails, the logging — cannot tell which one it is using. Switching between a simulated room and the real one is a single import line:

python 
# from fake_hardware import get_room     # simulated room
from real_hardware import get_room         # the actual Pi
Analogy. A flight simulator and a real cockpit with identical controls. The pilot's training transfers completely, because the interface never changed — only what sits behind it did. You develop against the simulator at your desk at midnight, then move to the real room with no code changes at all.

Where the language model joins in

Look back at the decision line: want_on = temp < SETPOINT. That is a rule someone wrote in advance, and it can only do the one thing it was written to do. It has no answer for a sensor that has stopped reporting, for two sensors disagreeing by ten degrees, or for smoke appearing while the heater runs.

The autonomous version replaces that one line with a question to a language model. The model is given the current readings and a list of tools it is permitted to use — read the sensors, set the heater, raise an alert — and it answers with which tool to call and a written reason. The perceive and act beats are unchanged; only the brain in the middle is swapped.

And this is precisely where the research question lives. A rule can be wrong, but it cannot be imaginative. A language model can command an actuator that does not exist, invent a state the hardware does not support, or confidently diagnose a fault from a reading it misread. That is why every action goes through a guarded tool layer that checks the actuator is on the whitelist, checks the requested state is legal, demands a written reason, and records the whole exchange in an append-only audit log. The model proposes; the guardrails decide what is allowed to reach the relay.

Which brings the project back to where step 1 started, now with a sharper question. The loop is still perceive, decide, act. What changed is that the deciding is no longer something we can read and verify in advance — so the engineering effort moves from writing the rule to constraining and observing whatever the model decides.
